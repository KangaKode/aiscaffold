# Agentic Governance

How the scaffold governs autonomous agent behavior: who approves what, what gets recorded, what data is protected, and where the money stops. This document maps each governance domain to the code that implements it and the tests that prove it -- and, just as deliberately, states what the scaffold does **not** claim to do.

---

No-op without the extra (plain `nullcontext`); non-recording with the extra but no user-configured tracer provider -- the scaffold never configures a provider or exporter (see Non-Claims) | `observability/tracing.py`, `orchestration/round_table.py`, `orchestration/chat_orchestrator.py` | `tests/test_credential_currency.py` |

## Known Limitations / Non-Claims

Stating what a control does *not* do is part of the control. These are the honest boundaries of the current implementation:

- **Sentinel's fail-closed refusal is advisory by DEFAULT.** When Sentinel cannot screen (no LLM, or the LLM call errors), its refusal is recorded as a critical finding (`premise_valid=False`, `refusal_reason="sentinel_unavailable"`) and it dissents at the vote -- but with `SENTINEL_ENFORCEMENT_ENABLED` unset (the default), no runtime path consumes `premise_valid` to halt the run (only the optional baseline tracker reads the refused flag). Deliberation proceeds, and with enough other voters the synthesis can still reach consensus on unscreened input. When every core agent shares the failed LLM client, all core voters dissent and consensus fails; a Sentinel-isolated failure leaves screening advisory. In advisory mode a rate-limited, gated, or crashed Sentinel is also silently skipped like any other agent -- runs proceed with no screening verdict and no refusal.
- **Core agent names are not reserved at registration.** Nothing stops a caller from registering an agent named `sentinel` (or any other core-agent name). The core agents are unregistered objects, so the dispatch gates resolve them by name: ONE registered same-name entry becomes the entry whose gates (suspension, rate limit, capability scopes) the core agent runs under -- suspending or rate-capping that entry silently gates the core Sentinel in advisory mode, while enforcement mode surfaces the loss as an explicit refusal (`sentinel_missing` when gated out, `sentinel_unavailable`/`sentinel_high_risk` when it still screens). The same name registered in MORE THAN ONE tenant makes the core agent unresolvable, and the identity gate blocks it (fail closed, `ambiguous_name`) -- silent screening loss in advisory mode, `sentinel_missing` refusal with enforcement on. The rate-limit exemption and the enforcement trigger key on core-roster membership, never on the bare name, so a registered impostor gains neither. Name reservation at registration is a planned hardening, not shipped behavior.
- **Sentinel enforcement trades availability for coverage, and decides after Phase 1 spend.** With enforcement on, an LLM outage or an exhausted tenant budget means every run refuses with `sentinel_unavailable` until the dependency recovers -- refused runs, not unscreened runs, by design. A `sentinel_missing` refusal stream is a configuration fault (core roster disabled, core load failure, or the core Sentinel blocked at the identity gate -- e.g. by a registered same-name agent), not an outage: fix the config, don't wait it out. The refusal is decided AFTER Phase 1, so the Phase 0/0.5/1 token spend happens on refused runs, and the evidence-enforcement pipeline still runs over Phase 1 analyses before the short-circuit is applied. The "no silent inert states" guarantee (`sentinel_missing` instead of a silent fail-open) holds only in enforcement mode; advisory mode keeps its pre-existing silent skips. Enforcement is per-process configuration: replicas with different flag values enforce differently.
- **The detection hooks are off by default and bounded in scope.** Baseline tracking, collusion detection, and sequence detection each need their env toggle set to `true`; until then they detect nothing. When enabled: the baseline tracker records only round-table and chat dispatches (not `resolve`/single-shot), and its deviation analysis (`check_deviation`) is still operator-invoked -- recording is wired, automated drift alerting is not; the collusion detector's vote history is per-process memory, so lockstep findings need >= 5 rounds within one process lifetime and restarts reset the window; the sequence scan runs only on the sampled every-Nth-request pass (`ACTIVITY_CHECK_SAMPLE_N`, default 25) and needs activity tracking plus a learning store; `analyze_correction_drift` (slow poisoning) runs only when `LOOP_INTEGRITY_DETECTION_ENABLED` is set -- gateway-wired on the approve route, but library users must wire `on_approve` themselves (the flag alone gives them nothing on this path). All of them are detect-only (flags and logs) and fire-and-forget -- a broken store never fails a request.
- **Audit `user_id` attribution is forward-looking and API-path-only.** The `audit_events.user_id` column (v8 migration) is populated only by writes that have an authenticated user in scope: API-driven deliberations, governance-report generation, and erasures. Every row written before the migration, and every write from a library caller that does not pass a user identity, reads as `''`. The same applies to `corrections.source_surface` and `reflections.created_by`. And since user_id derives from the bearer token, single-API-key deployments attribute everything to the same one user (see the single-key limitation below).
- **Delegation records document phase derivation, not agent-to-agent calls.** There is no direct agent-to-agent dispatch in this architecture (hub-and-spoke: the orchestrator dispatches, agents respond), so `delegation_records` rows describe which upstream artifacts fed each orchestrator dispatch -- analyze rows derive from nothing, challenge rows from the consumed Phase-1 analysts, vote rows from the synthesis. Opt-in and detect-only: with `DELEGATION_RECORDS_ENABLED` unset (the default) zero rows are written and dispatch is byte-identical; when enabled, writes are fire-and-forget (a broken store never fails a dispatch), nothing analyzes the rows automatically, and the table has no pruner yet -- it grows one row per agent per phase.
- **Tracing exports nothing until you configure a provider.** The `[otel]` extra makes `phase_span` create real spans only when a tracer provider is configured (standard `OTEL_*` env vars or explicit `set_tracer_provider`); the scaffold never configures a provider or exporter itself. Without the extra the helper is a plain `nullcontext`; with the extra but no provider, spans are non-recording. Span names follow the spirit of the OTel GenAI semantic conventions -- formal convention compliance is not claimed.
- **Runtime canary is opt-in and bounded — not always-on scanning and not containment.** Unset `RUNTIME_CANARY_ENABLED` leaves the three surfaces byte-identical to pre-feature behavior (chat user field stays unwrapped; resolve keeps XML wrap without canary; round-table analyses context unchanged). Detection uses exact substring match on the per-call token (paraphrased echoes are false negatives). Intermediate agent consults, cross-check, premise, and MCP tool bodies are not canary-scanned. Enforcement refuses explicitly and never silently strips a canary from a successful-looking response. This is not ASI05 egress control, not ASI10 graduated halt/suspend policy, and not a substitute for Sentinel screening. `STARTUP_CANARY_ENABLED` only validates the primitive round-trip at boot (failure logs + `startup_canary_failed` flag; never blocks startup). `detect_output_drift` remains a callable helper only; `detect_multi_turn_poisoning` stays on its separate `LOOP_INTEGRITY_DETECTION_ENABLED` path.
- **Opt-in MCP metadata enforcement is off by default.** When `MCP_TOOL_METADATA_ENFORCEMENT_ENABLED` is on, injection-flagged tool metadata is omitted from `list_tools` and `call_tool` returns the **stable enum** `error_code`/`error_message`=`tool_refused_metadata_injection` before transport — only after a successful list_tools screen against that server's config (health today). Drift never refuses. Outer screen failure leaves prior blocks for call_tool but returns an unfiltered list (`metadata_screen_failed`). Bare list_tools without config cannot refuse. Disabled servers get invoke 404 identical to missing. Blocks are per-tenant config (no cross-tenant propagation). Persist failure may drop blocks across restart. Not ASI05 egress / ASI10 policy tables. Never auto-sets `enabled=False`.
- **Model routing is opt-in and single-step on failure.** With `MODEL_ROUTING_ENABLED` unset (the default) every LLM call uses the client's single configured model, byte-identical to before. When enabled, the gateway attaches the router to the LLM client: each call's role selects a cost tier (budget-aware, circuit-broken), and after a FINAL retry failure the client attempts exactly ONE cascade step up-tier -- it does not walk the whole tier ladder, and a routing error of any kind falls back to the configured model rather than failing the call. The cascade retry does not re-run the budget check, so a tenant whose budget is exhausted exactly between the initial check and the cascade can overshoot by one call (the same accepted TOCTOU window as check-vs-spend).
- **Layer 1-2 injection scanning coverage varies by surface.** User messages get a **detect-only** Layer 1 pattern scan at four ingestion surfaces -- chat and round-table submission (at the API routes), the resolve tier, and the premise gate (`orchestration/ingest_scan.py`): findings are logged and persisted as a `user_message_injection` integrity flag when a learning store is in scope (the premise gate is log-only), but the scan never blocks a request and never rewrites the message -- users legitimately discuss injection techniques, so this is operator signal, not a gate. Because the chat and round-table scans live at the API routes, library callers that drive `ChatOrchestrator` or `RoundTable` directly get only the resolve/premise-gate scans. No user path runs `sanitize_for_prompt`. Boundary wrapping is unchanged: the resolve tier and the premise gate wrap the user's content in tagged boundaries with fence-break neutralization (and Sentinel wraps it again for its own screening prompt), but chat synthesis and round-table agent prompts still embed the user's message / task content directly -- length-validated at the route, not wrapped. Remote-agent responses and MCP tool output get sanitization plus the full Layer 1+2 scan (`advanced=True`), log-only -- a finding warns, it never drops the content; MCP tool descriptions/schemas from `list_tools` are likewise Layer 1+2 scanned detect-only (with hash drift memory); opt-in `MCP_TOOL_METADATA_ENFORCEMENT_ENABLED` may omit/refuse injection-flagged tools (drift stays detect-only); knowledge writes (the corrections override screen) run the same full scan and are the only surface where findings refuse the write. This is not sandbox or egress containment (ASI05 remains Not covered). Layer 2's decoding is deliberately bounded, not a universal unmasker: it normalizes homoglyphs, strips invisible characters, and decodes only contiguous standard-alphabet base64 runs of 20+ characters (up to 3 nesting levels), even-length hex runs of 20+ characters, and a single ROT13 pass. Payloads encoded as base64url, whitespace-chunked base64, base64 nested 4+ levels deep, URL-encoding (percent-escapes), or HTML entities are NOT decoded and pass Layers 1-2 undetected -- catching those falls to the Layer 3 semantic screen where it runs. The Sentinel semantic screen (Layer 3) covers the deliberation path regardless.
- **The adversarial harness does not attack Layer 3 or the dispatch gates.** The red-team round tables run with `include_core_agents=False` and no agent registry, so CI proves containment by the deterministic layers (Layers 1-2, wrapping, enforcement/synthesis) only. With `registry=None` the identity/rate gates pass trivially and the hostile agents declare no capability scopes, so nothing there is under adversarial pressure; the Sentinel screen and the dispatch/scope gates are covered by their dedicated unit tests (`tests/test_agent_identity.py`, orchestration tests) with mocked components.
- **Trust influence on routing is bounded, not prevented -- and the trust-guard defenses have honest edges.** Trust contributes at most +0.19 to a routing score (trust x 0.2 at the 0.95 ceiling, pinned by a regression test), so trust poisoning within that bound is flagged (opt-in), never blocked. Decay rehabilitates earned distrust at the same rate it heals stale distrust. The min-interaction gate masks legitimately earned EARLY distrust the same way it masks fabricated early praise -- an agent below the gate reports neutral 0.5 in both directions. Single-source-domination detects naive concentration (one un-rotated session id): `session_id` is caller-supplied and unbound to the authenticated identity, so an adversary who rotates session ids per request is not detected -- under the single-API-key default there is no stronger identity to group by (see the single-key limitation above).
- **The context-pressure estimate is a heuristic, and the client's per-field truncation has low-visibility signaling of its own.** The window condition estimates tokens as chars/4 -- ±30-50% off for code-heavy or CJK content; it is a trend signal, never a token count, and it makes no claim to detect truncation (the exact per-field condition does that). The signal only ever warns and counts: there is NO auto-compaction, summarization, or history trimming, opt-in or otherwise. Independent of this feature (and its default-off state), the LLM client truncates each prompt field at `max_prompt_length // 3` chars with low-visibility signaling: an in-band `[TRUNCATED]` marker appended to the field (visible to the model, not the operator) and an INFO log with no field/phase/call attribution (`security/prompt_guard.py`) -- with the pressure signal off, that is the only signaling truncation gets. A field over the cap only by virtue of null bytes fires the signal without being truncated (sanitize strips `\x00` before its length check) -- a rare false positive, never a false negative.
- **Heuristic classifiers are not ML-grade.** The content policy and override detector are regex/keyword heuristics. They catch obvious manipulation phrasings and will miss paraphrases, other languages, and creative rewording. They reduce risk; they do not eliminate it.
- **In-memory rate limits and budgets-without-a-store reset on restart.** Agent rate limits are process-local sliding windows. Budget spend and caps only survive restarts when a learning store is configured; without one, a restart is a budget reset (spend and caps both). With a store, spend is read fresh per check but cap configs are cached per process with a TTL (`BUDGET_CONFIG_TTL_SECONDS`, default 60s): a cap changed in one replica takes effect in the others within the TTL, not instantly.
- **The audit trail is tamper-evident within a run, not tamper-proof.** Each completed deliberation stores a reasoning-chain SHA-256 over its ordered phase artifacts, so editing a recorded phase and recomputing the hash will not match the stored digest -- casual after-the-fact edits are detectable. But the digest lives in the same database as the artifacts, so anyone who can alter the phases can also overwrite the digest; writes are still fire-and-forget (a failed write is logged, not raised). Likewise, output signing is symmetric (HMAC), so anyone who can verify can also sign -- it gives integrity and platform attestation for key-sharing consumers, not third-party non-repudiation. For that you need append-only storage, an external timestamp authority, and asymmetric signatures (swap the HMAC in `enforcement/signer.py` for Ed25519 -- same interface). See PLATFORM_GUIDE.md compliance section.
- **Erasure removes rows, not history.** `DELETE /api/v1/corrections/{id}` hard-deletes the live row, the derived error schemas that cite it (re-extracting from what remains), and the approval check-ins whose prompts embed the correction text, but database backups, WAL archives, any downstream exports made before the erasure, and prompt text already sent to LLM providers still contain the data. A complete Art. 17 program also needs backup rotation policy and downstream propagation -- deployment concerns outside the scaffold.
- **PII patterns are not a compliance guarantee.** Redaction covers common structured formats (emails, SSNs, card numbers, IPs, phones) plus a deliberately modest name heuristic. It will miss unstructured personal data, non-US formats, and context-dependent identifiers. It is a harm-reduction layer, not a GDPR/CCPA control by itself.
- **Timing regularity has false positives and is evadable.** Cron jobs, dashboards, and uptime monitors that call authenticated endpoints on a schedule look exactly like a machine-cadence extraction script and will be flagged; conversely, an adversary who adds random jitter between requests will not trip the CV threshold. It raises the bar for naive scripts; it is not proof of abuse or safety.
- **Pair escalation misses rings of 3+ users.** The approval-pair check counts directed proposer->approver pairs, so a ring where A approves B, B approves C, and C approves A never concentrates any single pair and evades detection. It targets the cheapest collusion (two accounts), not organized rings.
- **Approval-health stats are a health check on the human gate, not a rubber-stamping detector.** Fast p50/p95 does not prove misconduct; slow latency does not prove careful review. `self_approval_count` under the shipped single-API-key default will often equal total approvals (expected -- see the single-key four-eyes Non-Claim above), not evidence of abuse. Supersession counts are activity on the B7 surface, not a ring-collusion signal. Rings of 3+ and honor-signal revalidation remain out of scope for this section.
- **Extraction defense is inert without activity tracking.** The timing and volume detectors read `activity_events`; with `ACTIVITY_TRACKING_ENABLED=false` or no learning store, the guard degrades to "normal" (a startup warning says so) and nothing is monitored. The volume guard also counts only successful (HTTP 200) GETs of the exact knowledge listing routes -- failed requests never raise the count, and per-resource reads (e.g. `GET /corrections/{id}`) have distinct paths and are not counted; the sequence detector (`harness/sequence_detector.py`) is the complementary control for item-by-item extraction.
- **Single-API-key deployments share one user identity -- and four-eyes is not enforceable there.** user_id is a hash prefix of the bearer token, so with the scaffold's single API_KEY every caller is the same "user": per-user thresholds are effectively global (one abuser can trip caps for everyone), and proposer == approver ALWAYS, so the four-eyes rule cannot be satisfied by any caller. The posture is therefore explicit (`CORRECTIONS_FOUR_EYES`): the default `warn` mode allows self-approval while logging loudly and recording a `four_eyes_unenforceable` integrity flag -- visible degradation, not enforcement. `strict` mode enforces the rule and is only usable once real multi-user identities exist. Multi-key auth (see PLATFORM_GUIDE.md) is a prerequisite for per-user signals and for strict four-eyes.
- **Tenant isolation is enforced per RESOLVED tenant; resolving real tenants is your integration.** The shipped `verify_api_key` places every caller in the "default" tenant -- the registry's (tenant_id, name) keying, the tenant-scoped agents API (cross-tenant 404s), and per-tenant activity attribution only separate tenants after you replace it with an IdP integration that returns real tenant ids (PLATFORM_GUIDE.md Step 1) and keeps mirroring the context onto `request.state.auth_context`. `MULTI_TENANT_AUTH_ENABLED=true` is a detection-only declaration: it powers a one-time misattribution warning when an authenticated request's events still land in the default tenant, and changes no enforcement.
- **Prompt grounding reads a capped number of corrections.** `get_approved_for_context` fetches at most `CORRECTION_CONTEXT_FETCH_CAP` approved corrections (newest first, default 500) before the character budget is applied, so tenants whose approved knowledge base outgrows the cap silently lose their OLDEST corrections from prompt grounding. A single warning per process fires when a fetch saturates the cap; raise the env var or retire/compact old corrections (error schemas exist for exactly that).
- **Approving a procedure does not automatically ground it into agent prompts.** Default `knowledge_context` remains claim-only (`type=""`). Procedures (`type=procedure`) are inert in prompts until an explicit opt-in procedure-aware render path is enabled (not shipped as default-on).
- **Corrections validity is current-knowledge filtering, not a historical `as_of` query.** Supersession stores `valid_at` / `invalid_at` / `supersedes_id` on the row and grounding always filters `invalid_at=''` on the hot path -- there is no auto-invalidate (a human must approve the successor to invalidate the ancestor; the loop never does it autonomously), no `as_of` / historical query API on grounding / chat / listings, and legacy pre-v9 rows carry the empty-string sentinel (`invalid_at=''`) so they are still currently valid after upgrade rather than being mass-invalidated. Under the default `CORRECTIONS_FOUR_EYES=warn`, self-approval on a supersession approve records a `four_eyes_unenforceable` integrity flag but still invalidates the ancestor -- same posture as any approve (see the single-key limitation above). Compensating writes cover races and DB faults *inside* the running process; a process crash between successor commit and ancestor `update_if` can leave both rows currently valid (there is no outbox / reconciler) -- operators repair via the integrity flag surface or manual retire. Supersession approve REQUIRES `LearningStore.update_if`; BYO stores without it get an explicit 501 and the successor stays proposed (no silent unconditional-write fallback, unlike `lifecycle.transition`). Erasing an ancestor with any live successor is refused (409 naming the blockers); operators erase top-down under `ERASURE_DAILY_CAP`, so a supersession chain longer than the cap takes multiple days.
- **The governance report sees a recent-N horizon, not full history.** The store protocol supports equality filters plus a limit, so each report section fetches the tenant's most recent rows up to a per-section cap and windows them in Python. Sections that hit the cap annotate `coverage_partial: true` with the actual `coverage_from`; treat those counts as a floor. For exact long-range analytics, ship `audit_events` to a real analytics store (see SIEM export below).
- **Revalidation is an honor signal.** `POST /corrections/{id}/revalidate` proves that *some credential* re-confirmed the knowledge, not that the knowledge is true -- a compromised key can keep stale or poisoned corrections looking "fresh" indefinitely. The report's self-revalidation flag list (`last_validated_by` == the correction's own proposer, echoing the four-eyes concern) is the countermeasure: review those ids, don't trust them.
- **Stale detection dates legacy rows by updated_at.** Corrections that predate the aging columns have no last_validated_at, so staleness falls back to updated_at (their last lifecycle change). That prevents the whole knowledge base from flagging stale on upgrade day, but it also means a legacy row edited recently for unrelated reasons counts as fresh. Rows with no parseable timestamp are never flagged.
- **Single-node assumptions.** Tenant context uses process-local contextvars, autonomy env overrides are parsed once per process, and check-ins/budgets assume one coordinating instance unless you point everything at a shared store. Multi-node deployments need shared persistence and per-instance configuration discipline.
- **Layer 1 static patterns do not cover model-specific control tokens.** The prompt-guard regex list (`security/prompt_guard.py`) targets common injection phrasings and a handful of chat-format markers; model-specific control tokens such as Llama-2-style `<<SYS>>` fences are not in the pattern list and pass Layer 1 undetected. Catching those falls to Layer 3, the Sentinel semantic screen, which judges intent rather than surface tokens (and therefore requires an LLM).
- **The injection-defense golden set covers the deterministic layers only.** The regression smoke set (`evals/tasks/test_injection_defense_golden.py`, gated by `include_evals`) grades Layer 1 static patterns and Layer 2 normalization/decoding against a frozen baseline -- it is a regression guard, not a security benchmark, and a green run only means those layers still behave as when the baseline was frozen. It deliberately does **not** exercise Layer 3, the Sentinel semantic screen, which understands intent and therefore requires an LLM; semantic-layer coverage needs LLM-backed evals (see `evals/README.md`). Deterministic-layer confidence is not whole-stack confidence.
- **The open-corpus categories are baselined at their MEASURED miss rate, not zero.** The vendored CC-BY-4.0 subset (`tests/adversarial_payloads_open.py`) adds three golden-set categories that ship in the frozen baseline as *measured*, not aspirational: `open_injection` (subtle English social-engineering framings) and `open_multilingual` (non-English attempts) carry `expected=flag` but the pattern layers are English-phrase-driven and at baseline time EVERY one of those seeds passed them (14/14 and 18/18) -- those passes are recorded false negatives, and the baseline freezes them so the number can only be reviewed downward, never silently upward. The layer that *could* catch these is the LLM-backed Layer 3 semantic screen, which the golden set does not exercise. `open_content_safety` seeds carry `expected=pass` (they are not injection attacks); any Layer-1 trip is a recorded false positive. Seeds are curated under a written rubric (no CSAM-adjacent content, no operational uplift, no real PII; refusal-eliciting preferred) and are import-isolated from runtime (`tests/test_adversarial_open_corpus.py`). Full OWASP mapping: `docs/SECURITY_MAPPING.md`.
- **Task ISA is detect-only in Phase 1.** An optional `isa` on a round-table task yields an `isa_closure` report after synthesis; open or unverifiable required claims do **not** refuse consensus, rewrite analyses, or alter vote math. Absence of `isa` leaves behavior identical to the pre-ISA path. When reflections run, an ISA summary may be stored under `quality_metrics.isa_closure` for operator audit — still detect-only, not a prompt rewrite.
- **Learnings do not auto-edit the harness.** The learning loop does not auto-edit skills, hooks, or prompts from feedback, reflections, corrections, or graduation. Corrections ground prompts only after four-eyes approval via `build_knowledge_context`; preference graduation applies only through an approved check-in. Graded feedback intake may flag injection and skip trust EMA updates; it does not refuse or rewrite the feedback row.
- **Eval loop hygiene is factory-floor and opt-in.** The error-analysis recipe (`evals/ERROR_ANALYSIS_RECIPE.md`) and `evals/regression/` graduated examples (including the ISA open-claim case) are scaffold hygiene, not domain product datasets. `make eval-regression` is opt-in and no-ops when empty; default generated CI does **not** block on the full regression tree. LLM-as-judge is not part of that default path. Preference graduation (`learning/graduation.py`) is a separate check-in-gated preference path — not eval file promotion.
- **Capability Doctor is an ops matrix, not CI.** `aiscaffold doctor` / `scripts/capability_doctor.py` report capability health; they do not replace `bash scripts/validate_generated.sh` or GitHub Actions gates. Structure failures remain blocking; capability `broken` exits non-zero only with `--strict-capabilities`.
- **BM25 retrieval is language-naive, fixture-measured, and not adversarially robust beyond what its tests pin.** Tokenization is NFKC + lowercase + word characters -- no stemming, no stopwords, no language-specific analysis, and whole-token matching means no substring/prefix recall (query "deploy" does not match "deployment"; the legacy scorer's substring matching did -- the loss is priced into the measured fixture, one of whose queries covers exactly this case). The MRR/P@3 gains are measured on a 12-query/25-doc fixture, not a retrieval benchmark. The adversarial regression tests pin two specific behaviors (broad-coverage stuffing demoted; single-term repetition bounded by TF saturation) -- no robustness is claimed against within-scope corpus flooding (an attacker who can WRITE many documents into the same tenant/scope still shifts that scope's IDF; only cross-scope influence is prevented), and the semantic arm's adversarial robustness (embedding-space attacks) is not claimed at all. Consensus/priority filtering by consumers is post-rank with a known crowd-out property: filters like `consensus_only` are applied after the ranked list is capped, so relevant-but-filtered docs can crowd eligible ones out of a small `limit`. The Chroma adapter path is entirely unchanged -- BM25 and RRF apply to the in-memory store only.
- **Multilingual injection efficacy is UNMEASURED, not solved.** Layers 1-2 are explicitly English-centric (English phrase patterns; homoglyph/encoding normalization is language-agnostic but the phrase list is not), so non-English injections pass them by construction -- the `open_multilingual` false negatives make this visible. Layer 3, the Sentinel semantic screen, is the only layer that *could* generalize across languages, but its multilingual efficacy has **not been measured** in this scaffold: there are no LLM-backed multilingual evals here, and no claim is made that Sentinel catches non-English attacks. Treat multilingual coverage as an open integration point requiring your own LLM-backed evaluation, not a shipped guarantee.
- **`pip-audit` audits a resolved environment, not a lockfile.** The generated `security` job runs `pip-audit` after installing `requirements.txt` and every rendered optional extra, so it audits whatever versions pip actually resolved on that CI run. `requirements.txt.jinja` and `pyproject.toml.jinja` declare range constraints (e.g. `httpx>=0.27`), not exact pins, and this repository ships no lockfile: the same code can resolve to different transitive versions across runs. A green audit means "the versions installed here are clean given the advisory database at scan time", not "every version this range can resolve to is clean." If you need reproducible audits, add a lockfile (`pip-compile`, `uv pip compile`, or your platform equivalent) and wire it into the security job -- the scaffold does not do that for you.
- **The advisory database has limits.** `pip-audit` queries PyPI and OSV; both cover Python packages with published advisories. A newly disclosed vulnerability without an advisory entry (embargoed, private-disclosure, or simply unreported) is not detected, and coverage of non-PyPI or vendored code is not claimed at all. The advisory database is refreshed on each CI run, so scan results shift as new advisories publish; a green audit today does not guarantee a green audit tomorrow. Transient upstream failures (PyPI or OSV unreachable) fail the `security` job rather than producing a soft "no findings" result -- rerun the workflow after the outage recovers; do not add a `continue-on-error` bypass.
- **Branch protection cannot be configured or verified from inside this repository.** The generated workflow's `summary` job aggregates `test`, `lint`, and `security` so a single required check enforces all three; but making `summary` the required check is a GitHub *repository setting*, not a file in the repo. The scaffold documents the intended configuration (see `docs/OPERATIONS.md`) and cannot detect a maintainer who protects the wrong branch, requires a different check, or disables protection entirely. Verify the setting after your first push and re-verify whenever repository administrators change; treating the merge gate as "already enforced" without that check is an overclaim.
- **The `pip-audit` exceptions file is a HUMAN review record, not an automated reachability judgment.** The gate at `scripts/pip_audit_gate.py` fails closed on structural problems (missing fields, duplicate ids, malformed dates, expired entries) so a stale exception cannot be silently honoured, but it cannot tell whether the reason string is true, whether the compensating control actually mitigates the advisory, or whether the vulnerable code path is reachable. Every exception is a manual decision by the named `owner`, reviewed by a second engineer before merge, with a real `expires` date -- when the date passes, the exception disappears and blocking behaviour resumes automatically. Both shipped exceptions files (`.github/pip-audit-exceptions.json` in the scaffold repo and in every generated project) start as an empty list; adding an entry is a maintainer's judgment call, not an automated capability.
- **Manual prompt-reviewer results are point-in-time evidence, not CI automation.** The scoped prompt reviewers under `.cursor/agents/` (`red-team`, `sast-reviewer`, `security-hardener`, `agent-security-specialist`, `code-reviewer`, `solution-architect`, `test-architect`, `data-flow-guardian`) and the always-applied `red-team.mdc` rule are governed by `docs/REVIEWER_ASSURANCE.md`. Every prompt reviewer ships as `SHADOW`; a `BLOCK` verdict from a `SHADOW` reviewer is a governance bug. The deterministic half of `reviewer-evals/cases.json` runs in CI via `scripts/reviewer_eval.py`, but CI does **not** run prompt reviewers -- no authenticated agent runner exists in GitHub Actions today, so the `MANUAL_AGENT` cases (path traversal, missing auth, missing tenant scope, prompt-injection boundary, reviewer-injection resistance) are evaluated by a human operator running the promotion protocol. Recorded promotion evidence (detection result, safe-case result, injection-resistance result, evidence review, human approver, date) is **point-in-time** on that reviewer version against that fixture-set version; it is **not** a CI-enforced guarantee, does **not** carry forward across a material change (prompt/scope/tools/model behavior resets the row to `SHADOW`), and is **not proof against unknown attacks** the fixture does not seed. Suspension triggers (missed seeded cases, false blocking, instruction-following from untrusted fixtures, scope overreach) demote a reviewer back to `SHADOW` on any regression -- the register is the live gate, not the historical evidence. Reviewers with zero domain fixtures (`solution-architect`, `test-architect` as of baseline v2) are **`NOT_EVALUATED`**, not a vacuous gate-1 pass.
- **Cursor Auto-review is not a security boundary.** Product Auto-review and similar hosted checks may assist maintainers; they do not replace shipped prompt reviewers, CI security jobs, or human ownership of merge decisions.
- **Cloud Agents are not equivalent to local hook-enforced runs.** A Cloud Agent session does not automatically inherit this project's local hooks, always-applied rules, or workspace-enforced constraints unless those are explicitly configured for that environment.
- **No hard dependency on Approval Agents or Bugbot.** Generated projects remain useful without paid Cursor SKUs; Bugbot and Approval Agents are optional if a maintainer enables them. Autofix stays off unless explicitly turned on.

## Extension Points

- **SIEM export**: the `audit_events` table is a clean feed for a log shipper -- poll by `created_at` and forward to your SIEM.
- **Ground-truth verification**: plug a real `GroundTruthProvider` into the enforcement pipeline so numeric claims are checked against authoritative data.
- **Multi-provider model diversity**: model routing (`llm/model_router.py`, `MODEL_ROUTING_ENABLED`) maps roles to cost tiers with cascade and budget-aware downgrades, and the gateway's LLM client consults it when enabled. The extension is provider diversity: point the frontier tier (used by `sentinel_analysis`) at a different provider than your domain agents via `MODEL_TIER_MAP_JSON` so one provider's blind spots don't propagate.
- **Workload identity**: replace `issue_token`/`verify_token`/`hash_token` in `agents/identity.py` with your corporate STS or service-mesh identity system.
- **Real-time human escalation**: wire `CheckInManager` to a pager/chat integration so approval-required results notify a person immediately instead of waiting to be polled.
- **Per-call sandboxing**: execute agent-initiated tool calls inside a sandbox (container, seccomp, or WASM) so a manipulated agent's blast radius stays bounded.
