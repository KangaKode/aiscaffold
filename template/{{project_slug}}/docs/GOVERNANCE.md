# Agentic Governance

How the scaffold governs autonomous agent behavior: who approves what, what gets recorded, what data is protected, and where the money stops. This document maps each governance domain to the code that implements it and the tests that prove it -- and, just as deliberately, states what the scaffold does **not** claim to do.

## Known Limitations / Non-Claims

Stating what a control does *not* do is part of the control. These are the honest boundaries of the current implementation:

- **Sentinel's fail-closed refusal is advisory by DEFAULT.** When Sentinel cannot screen (no LLM, or the LLM call errors), its refusal is recorded as a critical finding (`premise_valid=False`, `refusal_reason="sentinel_unavailable"`) and it dissents at the vote -- but with `SENTINEL_ENFORCEMENT_ENABLED` unset (the default), no runtime path consumes `premise_valid` to halt the run (only the optional baseline tracker reads the refused flag). Deliberation proceeds, and with enough other voters the synthesis can still reach consensus on unscreened input. When every core agent shares the failed LLM client, all core voters dissent and consensus fails; a Sentinel-isolated failure leaves screening advisory. In advisory mode a rate-limited, gated, or crashed Sentinel is also silently skipped like any other agent -- runs proceed with no screening verdict and no refusal.
- **Core agent names are not reserved at registration.** Nothing stops a caller from registering an agent named `sentinel` (or any other core-agent name). The core agents are unregistered objects, so the dispatch gates resolve them by name: ONE registered same-name entry becomes the entry whose gates (suspension, rate limit, capability scopes) the core agent runs under -- suspending or rate-capping that entry silently gates the core Sentinel in advisory mode, while enforcement mode surfaces the loss as an explicit refusal (`sentinel_missing` when gated out, `sentinel_unavailable`/`sentinel_high_risk` when it still screens). The same name registered in MORE THAN ONE tenant makes the core agent unresolvable, and the identity gate blocks it (fail closed, `ambiguous_name`) -- silent screening loss in advisory mode, `sentinel_missing` refusal with enforcement on. The rate-limit exemption and the enforcement trigger key on core-roster membership, never on the bare name, so a registered impostor gains neither. Name reservation at registration is a planned hardening, not shipped behavior.
- **Sentinel enforcement trades availability for coverage, and decides after Phase 1 spend.** With enforcement on, an LLM outage or an exhausted tenant budget means every run refuses with `sentinel_unavailable` until the dependency recovers -- refused runs, not unscreened runs, by design. A `sentinel_missing` refusal stream is a configuration fault (core roster disabled, core load failure, or the core Sentinel blocked at the identity gate -- e.g. by a registered same-name agent), not an outage: fix the config, don't wait it out. The refusal is decided AFTER Phase 1, so the Phase 0/0.5/1 token spend happens on refused runs, and the evidence-enforcement pipeline still runs over Phase 1 analyses before the short-circuit is applied. The "no silent inert states" guarantee (`sentinel_missing` instead of a silent fail-open) holds only in enforcement mode; advisory mode keeps its pre-existing silent skips. Enforcement is per-process configuration: replicas with different flag values enforce differently.
- **The detection hooks are off by default and bounded in scope.** Baseline tracking, collusion detection, and sequence detection each need their env toggle set to `true`; until then they detect nothing. When enabled: the baseline tracker records only round-table and chat dispatches (not `resolve`/single-shot), and its deviation analysis (`check_deviation`) is still operator-invoked -- recording is wired, automated drift alerting is not; the collusion detector's vote history is per-process memory, so lockstep findings need >= 5 rounds within one process lifetime and restarts reset the window; the sequence scan runs only on the sampled every-Nth-request pass (`ACTIVITY_CHECK_SAMPLE_N`, default 25) and needs activity tracking plus a learning store; `analyze_correction_drift` (slow poisoning) remains a library with no runtime call site. All of them are detect-only (flags and logs) and fire-and-forget -- a broken store never fails a request.
- **Audit `user_id` attribution is forward-looking and API-path-only.** The `audit_events.user_id` column (v8 migration) is populated only by writes that have an authenticated user in scope: API-driven deliberations, governance-report generation, and erasures. Every row written before the migration, and every write from a library caller that does not pass a user identity, reads as `''`. The same applies to `corrections.source_surface` and `reflections.created_by`. And since user_id derives from the bearer token, single-API-key deployments attribute everything to the same one user (see the single-key limitation below).
- **Delegation records document phase derivation, not agent-to-agent calls.** There is no direct agent-to-agent dispatch in this architecture (hub-and-spoke: the orchestrator dispatches, agents respond), so `delegation_records` rows describe which upstream artifacts fed each orchestrator dispatch -- analyze rows derive from nothing, challenge rows from the consumed Phase-1 analysts, vote rows from the synthesis. Opt-in and detect-only: with `DELEGATION_RECORDS_ENABLED` unset (the default) zero rows are written and dispatch is byte-identical; when enabled, writes are fire-and-forget (a broken store never fails a dispatch), nothing analyzes the rows automatically, and the table has no pruner yet -- it grows one row per agent per phase.
- **Tracing exports nothing until you configure a provider.** The `[otel]` extra makes `phase_span` create real spans only when a tracer provider is configured (standard `OTEL_*` env vars or explicit `set_tracer_provider`); the scaffold never configures a provider or exporter itself. Without the extra the helper is a plain `nullcontext`; with the extra but no provider, spans are non-recording. Span names follow the spirit of the OTel GenAI semantic conventions -- formal convention compliance is not claimed.
- **The canary check is a startup self-test, not runtime output scanning.** `STARTUP_CANARY_ENABLED=true` verifies once at gateway startup that the canary machinery round-trips (injection, outbound-sanitization survival, leak detection, token uniqueness) and records a `startup_canary_failed` integrity flag on failure -- it never checks a live LLM response. No runtime path embeds canaries in real prompts or calls `check_canary` on real responses, and `detect_output_drift` / `detect_multi_turn_poisoning` ship as callable helpers only. Runtime canary leakage detection remains an integration point for your prompt/response pipeline.
- **Model routing is opt-in and single-step on failure.** With `MODEL_ROUTING_ENABLED` unset (the default) every LLM call uses the client's single configured model, byte-identical to before. When enabled, the gateway attaches the router to the LLM client: each call's role selects a cost tier (budget-aware, circuit-broken), and after a FINAL retry failure the client attempts exactly ONE cascade step up-tier -- it does not walk the whole tier ladder, and a routing error of any kind falls back to the configured model rather than failing the call. The cascade retry does not re-run the budget check, so a tenant whose budget is exhausted exactly between the initial check and the cascade can overshoot by one call (the same accepted TOCTOU window as check-vs-spend).
- **Layer 1-2 injection scanning coverage varies by surface.** User messages get a **detect-only** Layer 1 pattern scan at four ingestion surfaces -- chat and round-table submission (at the API routes), the resolve tier, and the premise gate (`orchestration/ingest_scan.py`): findings are logged and persisted as a `user_message_injection` integrity flag when a learning store is in scope (the premise gate is log-only), but the scan never blocks a request and never rewrites the message -- users legitimately discuss injection techniques, so this is operator signal, not a gate. Because the chat and round-table scans live at the API routes, library callers that drive `ChatOrchestrator` or `RoundTable` directly get only the resolve/premise-gate scans. No user path runs `sanitize_for_prompt`. Boundary wrapping is unchanged: the resolve tier and the premise gate wrap the user's content in tagged boundaries with fence-break neutralization (and Sentinel wraps it again for its own screening prompt), but chat synthesis and round-table agent prompts still embed the user's message / task content directly -- length-validated at the route, not wrapped. Remote-agent responses and MCP tool output get sanitization plus the full Layer 1+2 scan (`advanced=True`), log-only -- a finding warns, it never drops the content; knowledge writes (the corrections override screen) run the same full scan and are the only surface where findings refuse the write. Layer 2's decoding is deliberately bounded, not a universal unmasker: it normalizes homoglyphs, strips invisible characters, and decodes only contiguous standard-alphabet base64 runs of 20+ characters (up to 3 nesting levels), even-length hex runs of 20+ characters, and a single ROT13 pass. Payloads encoded as base64url, whitespace-chunked base64, base64 nested 4+ levels deep, URL-encoding (percent-escapes), or HTML entities are NOT decoded and pass Layers 1-2 undetected -- catching those falls to the Layer 3 semantic screen where it runs. The Sentinel semantic screen (Layer 3) covers the deliberation path regardless.
- **The adversarial harness does not attack Layer 3 or the dispatch gates.** The red-team round tables run with `include_core_agents=False` and no agent registry, so CI proves containment by the deterministic layers (Layers 1-2, wrapping, enforcement/synthesis) only. With `registry=None` the identity/rate gates pass trivially and the hostile agents declare no capability scopes, so nothing there is under adversarial pressure; the Sentinel screen and the dispatch/scope gates are covered by their dedicated unit tests (`tests/test_agent_identity.py`, orchestration tests) with mocked components.
- **Trust influence on routing is bounded, not prevented -- and the trust-guard defenses have honest edges.** Trust contributes at most +0.19 to a routing score (trust x 0.2 at the 0.95 ceiling, pinned by a regression test), so trust poisoning within that bound is flagged (opt-in), never blocked. Decay rehabilitates earned distrust at the same rate it heals stale distrust. The min-interaction gate masks legitimately earned EARLY distrust the same way it masks fabricated early praise -- an agent below the gate reports neutral 0.5 in both directions. Single-source-domination detects naive concentration (one un-rotated session id): `session_id` is caller-supplied and unbound to the authenticated identity, so an adversary who rotates session ids per request is not detected -- under the single-API-key default there is no stronger identity to group by (see the single-key limitation above).
- **Heuristic classifiers are not ML-grade.** The content policy and override detector are regex/keyword heuristics. They catch obvious manipulation phrasings and will miss paraphrases, other languages, and creative rewording. They reduce risk; they do not eliminate it.
- **In-memory rate limits and budgets-without-a-store reset on restart.** Agent rate limits are process-local sliding windows. Budget spend and caps only survive restarts when a learning store is configured; without one, a restart is a budget reset (spend and caps both). With a store, spend is read fresh per check but cap configs are cached per process with a TTL (`BUDGET_CONFIG_TTL_SECONDS`, default 60s): a cap changed in one replica takes effect in the others within the TTL, not instantly.
- **The audit trail is tamper-evident within a run, not tamper-proof.** Each completed deliberation stores a reasoning-chain SHA-256 over its ordered phase artifacts, so editing a recorded phase and recomputing the hash will not match the stored digest -- casual after-the-fact edits are detectable. But the digest lives in the same database as the artifacts, so anyone who can alter the phases can also overwrite the digest; writes are still fire-and-forget (a failed write is logged, not raised). Likewise, output signing is symmetric (HMAC), so anyone who can verify can also sign -- it gives integrity and platform attestation for key-sharing consumers, not third-party non-repudiation. For that you need append-only storage, an external timestamp authority, and asymmetric signatures (swap the HMAC in `enforcement/signer.py` for Ed25519 -- same interface). See PLATFORM_GUIDE.md compliance section.
- **Erasure removes rows, not history.** `DELETE /api/v1/corrections/{id}` hard-deletes the live row, the derived error schemas that cite it (re-extracting from what remains), and the approval check-ins whose prompts embed the correction text, but database backups, WAL archives, any downstream exports made before the erasure, and prompt text already sent to LLM providers still contain the data. A complete Art. 17 program also needs backup rotation policy and downstream propagation -- deployment concerns outside the scaffold.
- **PII patterns are not a compliance guarantee.** Redaction covers common structured formats (emails, SSNs, card numbers, IPs, phones) plus a deliberately modest name heuristic. It will miss unstructured personal data, non-US formats, and context-dependent identifiers. It is a harm-reduction layer, not a GDPR/CCPA control by itself.
- **Timing regularity has false positives and is evadable.** Cron jobs, dashboards, and uptime monitors that call authenticated endpoints on a schedule look exactly like a machine-cadence extraction script and will be flagged; conversely, an adversary who adds random jitter between requests will not trip the CV threshold. It raises the bar for naive scripts; it is not proof of abuse or safety.
- **Pair escalation misses rings of 3+ users.** The approval-pair check counts directed proposer->approver pairs, so a ring where A approves B, B approves C, and C approves A never concentrates any single pair and evades detection. It targets the cheapest collusion (two accounts), not organized rings.
- **Extraction defense is inert without activity tracking.** The timing and volume detectors read `activity_events`; with `ACTIVITY_TRACKING_ENABLED=false` or no learning store, the guard degrades to "normal" (a startup warning says so) and nothing is monitored. The volume guard also counts only successful (HTTP 200) GETs of the exact knowledge listing routes -- failed requests never raise the count, and per-resource reads (e.g. `GET /corrections/{id}`) have distinct paths and are not counted; the sequence detector (`harness/sequence_detector.py`) is the complementary control for item-by-item extraction.
- **Single-API-key deployments share one user identity -- and four-eyes is not enforceable there.** user_id is a hash prefix of the bearer token, so with the scaffold's single API_KEY every caller is the same "user": per-user thresholds are effectively global (one abuser can trip caps for everyone), and proposer == approver ALWAYS, so the four-eyes rule cannot be satisfied by any caller. The posture is therefore explicit (`CORRECTIONS_FOUR_EYES`): the default `warn` mode allows self-approval while logging loudly and recording a `four_eyes_unenforceable` integrity flag -- visible degradation, not enforcement. `strict` mode enforces the rule and is only usable once real multi-user identities exist. Multi-key auth (see PLATFORM_GUIDE.md) is a prerequisite for per-user signals and for strict four-eyes.
- **Tenant isolation is enforced per RESOLVED tenant; resolving real tenants is your integration.** The shipped `verify_api_key` places every caller in the "default" tenant -- the registry's (tenant_id, name) keying, the tenant-scoped agents API (cross-tenant 404s), and per-tenant activity attribution only separate tenants after you replace it with an IdP integration that returns real tenant ids (PLATFORM_GUIDE.md Step 1) and keeps mirroring the context onto `request.state.auth_context`. `MULTI_TENANT_AUTH_ENABLED=true` is a detection-only declaration: it powers a one-time misattribution warning when an authenticated request's events still land in the default tenant, and changes no enforcement.
- **Prompt grounding reads a capped number of corrections.** `get_approved_for_context` fetches at most `CORRECTION_CONTEXT_FETCH_CAP` approved corrections (newest first, default 500) before the character budget is applied, so tenants whose approved knowledge base outgrows the cap silently lose their OLDEST corrections from prompt grounding. A single warning per process fires when a fetch saturates the cap; raise the env var or retire/compact old corrections (error schemas exist for exactly that).
- **The governance report sees a recent-N horizon, not full history.** The store protocol supports equality filters plus a limit, so each report section fetches the tenant's most recent rows up to a per-section cap and windows them in Python. Sections that hit the cap annotate `coverage_partial: true` with the actual `coverage_from`; treat those counts as a floor. For exact long-range analytics, ship `audit_events` to a real analytics store (see SIEM export below).
- **Revalidation is an honor signal.** `POST /corrections/{id}/revalidate` proves that *some credential* re-confirmed the knowledge, not that the knowledge is true -- a compromised key can keep stale or poisoned corrections looking "fresh" indefinitely. The report's self-revalidation flag list (`last_validated_by` == the correction's own proposer, echoing the four-eyes concern) is the countermeasure: review those ids, don't trust them.
- **Stale detection dates legacy rows by updated_at.** Corrections that predate the aging columns have no last_validated_at, so staleness falls back to updated_at (their last lifecycle change). That prevents the whole knowledge base from flagging stale on upgrade day, but it also means a legacy row edited recently for unrelated reasons counts as fresh. Rows with no parseable timestamp are never flagged.
- **Single-node assumptions.** Tenant context uses process-local contextvars, autonomy env overrides are parsed once per process, and check-ins/budgets assume one coordinating instance unless you point everything at a shared store. Multi-node deployments need shared persistence and per-instance configuration discipline.
- **Layer 1 static patterns do not cover model-specific control tokens.** The prompt-guard regex list (`security/prompt_guard.py`) targets common injection phrasings and a handful of chat-format markers; model-specific control tokens such as Llama-2-style `<<SYS>>` fences are not in the pattern list and pass Layer 1 undetected. Catching those falls to Layer 3, the Sentinel semantic screen, which judges intent rather than surface tokens (and therefore requires an LLM).
- **The injection-defense golden set covers the deterministic layers only.** The regression smoke set (`evals/tasks/test_injection_defense_golden.py`, gated by `include_evals`) grades Layer 1 static patterns and Layer 2 normalization/decoding against a frozen baseline -- it is a regression guard, not a security benchmark, and a green run only means those layers still behave as when the baseline was frozen. It deliberately does **not** exercise Layer 3, the Sentinel semantic screen, which understands intent and therefore requires an LLM; semantic-layer coverage needs LLM-backed evals (see `evals/README.md`). Deterministic-layer confidence is not whole-stack confidence.

## Extension Points

- **SIEM export**: the `audit_events` table is a clean feed for a log shipper -- poll by `created_at` and forward to your SIEM.
- **Ground-truth verification**: plug a real `GroundTruthProvider` into the enforcement pipeline so numeric claims are checked against authoritative data.
- **Multi-provider model diversity**: model routing (`llm/model_router.py`, `MODEL_ROUTING_ENABLED`) maps roles to cost tiers with cascade and budget-aware downgrades, and the gateway's LLM client consults it when enabled. The extension is provider diversity: point the frontier tier (used by `sentinel_analysis`) at a different provider than your domain agents via `MODEL_TIER_MAP_JSON` so one provider's blind spots don't propagate.
- **Workload identity**: replace `issue_token`/`verify_token`/`hash_token` in `agents/identity.py` with your corporate STS or service-mesh identity system.
- **Real-time human escalation**: wire `CheckInManager` to a pager/chat integration so approval-required results notify a person immediately instead of waiting to be polled.
- **Per-call sandboxing**: execute agent-initiated tool calls inside a sandbox (container, seccomp, or WASM) so a manipulated agent's blast radius stays bounded.
